# 赛前模拟舱 · 技术实现文档

> 作品：赛前模拟舱——AI 评委团路演陪练训练系统
> 赛道：大学生 OPC 创新创业 AI Agent 赛道
> 文档版本：v1.0（2026-11-04，与当前仓库代码一致）

## 1. 项目概述

赛前模拟舱面向高校双创竞赛与课程答辩场景，用 AI Agent 把「评委视角的陪练」产品化，覆盖 **诊断 → 陪练 → 复盘 → 归档** 完整训练闭环：

1. **诊断**：粘贴 BP、选择目标赛事，诊断官按该赛事官方评分维度逐项打分，输出总分、维度分与漏洞清单（每条漏洞附带「评委最可能问的问题」）。
2. **陪练**：进入 AI 评委席，技术 / 商业 / 投资人三种人设轮换提问，逐题评分并追问；普通与地狱两档强度。
3. **复盘**：根据问答实录生成评分卡、逐题点评、AI 参考回答与漏洞清单；漏洞由用户人工确认后写入档案。
4. **归档**：多场次得分曲线、漏洞闭环率、场次与 BP 原文管理，上一场未闭合漏洞会进入下一场追问，形成跨场次闭环。

**核心规模**：6 套赛事评分标准、87 道评委高频题（通用 61 + OPC 定向 20 + 蓝桥杯定向 6）、3 种评委人设、2 档难度、4 张本地数据表、3 条 AI API 路由。

**架构要点**

- **前后端同仓**：Next.js App Router 同时承载页面与 API 路由，部署单个 Node 服务即可。
- **无数据库**：训练记录全部存于浏览器 `localStorage`；服务端不持久化任何用户数据。
- **Key 只在服务端**：`DEEPSEEK_API_KEY` 由 API 路由读取，浏览器端永远拿不到。
- **演示模式兜底**：未配置 Key 或模型调用失败时，路由返回结构一致的模拟数据并打 `mock` 标记，前端展示「演示模式」横幅，保证产品可演示。
- **双模式数据层**（`lib/data-layer.ts`）：登录用户走 Supabase 云端（`lib/db` 云实现 + RLS）；未登录/未配置自动落回 localStorage 本地实现——同一 `DataLayer` 接口，页面无感知。详见 `docs/supabase-数据系统方案.md`。

## 5. 数据模型与本地存储

### 5.2 存储实现（`lib/store.ts`）

- 键名：`lp_teams`、`lp_sessions`、`lp_qa_records`、`lp_weakness_items`。
- 读写：`read<T>(key)` 带 `try/catch`（JSON 损坏时返回空数组）；`write` 整体覆盖写回。
- 主键生成：`uid(prefix)` = `prefix_` + 时间戳 36 进制 + 5 位随机串。
- 级联删除：
  - 删除团队：清理该团队的 sessions、这些 sessions 的 qa_records、该团队的 weakness_items。
  - 删除场次：清理该场 session、其 qa_records、`session_id` 匹配的 weakness_items。
- 统计：`weaknessTable.stats(team_id)` 排除 `invalid`，返回 `{ total, closed, rate }`。

### 5.3 状态机

```
diagnosed ──首题作答──▶ practicing ──生成复盘──▶ practiced ──复盘生成完成──▶ reviewed
     ▲                      │                                              │
     └──── 直接进入复盘 ─────┘（无问答记录时不可复盘，前端拦截）
```

### 5.4 数据层抽象（`lib/data-layer.ts`）

页面统一通过 `useDataLayer()` 获取 `DataLayer` 接口（`team / session / qa / weakness` 四个异步仓储），按登录态自动选择实现：

- **本地实现** `createLocalLayer()`：包装 `lib/store.ts`（未登录、未配置 Supabase、演示兜底）。
- **云端实现** `createCloudLayer()`：`@supabase/supabase-js` 读写 Postgres，owner 由 `default auth.uid()` 注入，安全性由 RLS 保证。
- **登录**：`lib/auth-context.tsx` 的 `AuthProvider/useAuth`（邮箱 + 密码）；登录页 `app/auth/page.tsx`。
- **建表 SQL**：`supabase/migrations/0001_init.sql`（含 RLS 全量策略）。
- **一次性迁移**：`importLocalToCloud()`——登录后检测本地数据，按 teams → sessions → qa → weaknesses 顺序导入云端（幂等，`lp_migrated_to` 标记）。

## 6. 核心业务流程

### 6.1 新建训练与诊断（`app/new/page.tsx` → `POST /api/diagnose`）

1. 表单字段：团队名称、目标赛事、BP 文本（支持 `.txt/.md` 上传，前端 `File.text()` 读取）、训练强度、首选评委。
2. 前端校验：队名非空；BP ≥ 50 字。
3. 请求 `/api/diagnose`，body 为 `{ bp_text, competition }`。
4. 成功后：
   - `teamTable.create(name)`：同名团队复用，否则新建；
   - 生成 `session_id`，写入完整 `Session`（含 diagnosis、overall_score、dimension_scores，status=`diagnosed`）；
   - `router.push('/report/<id>')`。
5. 失败：展示接口错误，恢复表单可编辑。

### 6.2 诊断报告（`app/report/[id]/page.tsx`）

- 从 `sessionTable.get(id)` 读取场次；无诊断数据时展示空态与返回入口。
- 展示：综合分（ScoreRing）、五维雷达（RadarChart）、五维评分条（ScoreBars）、优势列表、漏洞清单（严重度标签 + `expect_question`）。
- 页脚 CTA 进入 `/practice/<id>`。
- 报告若为 mock（无 Key/调用失败），顶部显示 MockBanner。

### 6.3 模拟陪练（`app/practice/[id]/page.tsx`）

**状态**：`bubbles`（对话流）、`records`（已答题目）、`pendingQuestion`（等待回答的问题）、`busy`、`ended`、`mock`。

**进入页面**

- 无历史记录：调用 `POST /api/judge`（phase=`start`），展示首题；`startedRef` 防止 React StrictMode 重复请求。
- 有历史记录：按 `qa_records` 重放对话，直接置为已结束状态（当前版本不恢复未答问题）。

**作答流程（`send()`）**

1. 校验：输入非空、存在 `pendingQuestion`、非 busy/ended。
2. 生成 `QARecord`（round = 已有记录数 + 1），立即写入 localStorage 并更新 UI。
3. 组装 `asked` 历史，调用 `/api/judge`（phase=`answer`，携带 `pending_question` 与 `user_answer`）。
4. 返回后：把 `score/comment` 回写到该题记录（从 localStorage 现读，避免闭包陈旧值），`score ≤ 2` 置 `weakness_flag=true`。
5. 根据 `action`：
   - `followup` / `next`：追加评委评语气泡与新问题，更新 `pendingQuestion`；
   - `end`：置 `ended`，展示「生成复盘报告」入口。
6. 首题作答后将会话状态置为 `practicing`。

**切人设（`switchPersona`）**：更新 session.persona，调用 phase=`switch` 获取新评委的下一题，评分返回 null。

**切难度（`switchMode`）**：本地切换 `normal ↔ hell` 并写入 session，追加系统提示；题数上限随模式变化（普通 9 题、地狱 10 题）。

**结束**：`finish()` 将会话置为 `practiced`、写入 `total_rounds`，跳转 `/review/<id>`。

### 6.4 复盘（`app/review/[id]/page.tsx` → `POST /api/review`）

1. 读取场次与问答记录；收集该团队**本场之前**未闭合漏洞（`confirmed`/`open`）。
2. 读取上一场同团队复盘的维度分之和作为对比分 `prevScore`（同量纲：答辩表现分，而非 BP 诊断分）。
3. 若场次已有 `review` 直接使用；否则请求 `/api/review`，body 含赛事、BP 摘要、诊断总分、上一场得分、逐题记录、历史漏洞描述。
4. 返回后写入 `session.review`，状态置 `reviewed`；`reviewedRef` 防止 StrictMode 重复请求。
5. 展示：
   - 本场评分（上一场 → 本场 + 差值）；
   - 逐题点评与 AI 参考回答（默认折叠，标注「AI 生成，仅供参考」）；
   - 漏洞确认：人工点「成立，记入档案」或「不成立，忽略」，确认后写入 `weakness_items`；
   - 上场漏洞追踪：AI 判断 `recurred/improved/untouched`，用户可标记「已补上，闭环」；
   - 导出 Markdown、打印/存 PDF。
6. 导出文件名：`赛前模拟舱-复盘-{团队名}-{session_id}.md`。

### 6.5 训练档案（`app/archive/page.tsx`）

- 团队切换；三项指标：累计训练、最新综合得分（含环比箭头）、漏洞闭环率。
- 综合得分曲线：口径为各场 BP 诊断分（与复盘答辩表现分相互独立），SVG 折线图 `TrendChart`。
- 漏洞追踪：列出非 `invalid` 漏洞，可标记已解决。
- 场次列表：赛事/模式/人设、时间、状态、诊断分，支持查看 BP 原文弹层、进入诊断/陪练/复盘、删除（原生 `confirm` 二次确认）。
- 删除团队或场次时执行级联清理。

## 7. AI Agent 设计

### 7.1 模型调用层（`lib/ai.ts`）

- 使用 `openai` SDK 指向 DeepSeek 兼容端点；Key 仅服务端读取。
- `chatJSON(system, user, { maxTokens, temperature })`：
  - `response_format: { type: "json_object" }` 强制 JSON；
  - 默认 `model = deepseek-chat`；
  - 返回后交给 `parseJSONLoose` 解析。
- `parseJSONLoose` 处理模型偶发包裹 ```json 围栏或前后杂讯：先直接 `JSON.parse`，失败则截取第一个 `{` 到最后一个 `}` 再解析；仍失败抛出带截断原文的错误。

### 7.2 三个 Agent 的角色与约束

| Agent | 职责 | 关键约束 |
| --- | --- | --- |
| 诊断官 | 按赛事评分标准逐维打分、给优势/漏洞与「最可能追问」 | 只依据 BP 文本；未提及维度按缺失扣分；漏洞必须可追问；60 字内直白表达 |
| 评委 | 三态推进（followup / next / end），逐题评分与点评 | 只提问与点评、绝不替用户回答；不编造 BP 外细节；不重复已问题；每次只问一个问题 |
| 复盘官 | 汇总实录生成评分卡、逐题点评、参考回答、漏洞清单与下场建议 | 漏洞必须对应 `source_round`；参考回答只使用 BP 真实信息，缺数据须如实标注；历史漏洞判定原样回填 |

### 7.3 提示词结构

三条路由均采用「系统提示词承载规则与 Schema + 用户消息承载当次输入」：

**诊断**：赛事名 → 评分维度与细则 → 评审导向 → 案例特征（获奖共性/常见减分项）→ 硬性规则 → 输出 JSON Schema → BP 正文（截断 8000 字）。

**评委**：人设 brief → 人设标签 → 难度规则 → BP 摘要与诊断弱点（优先定向）→ 高频题库弹药（最多 18 题，排除已问）→ 出题策略（约 60% 弱点 / 40% 题库）→ 红线 → 已完成问答记录 → JSON Schema → 当前阶段指令（start/switch/answer）与题数上限。

**复盘**：评分维度 → BP 摘要 → 本场问答实录 → 历史未闭合漏洞 → 硬性规则（含参考回答与复发判定要求）→ JSON Schema → 上一场得分提示。

### 7.4 结构化输出与确定性校验（Sanitize）

三个路由都不直接信任模型输出，返回前统一做确定性校验：

- **诊断**（`sanitize`）：
  - 维度按赛事标准重建，缺失维度按满分 60% 兜底；
  - 每个维度分 `clamp(0, max)`；
  - 总分优先用模型值，否则按维度加权折算；
  - strengths 截断 3 条、weaknesses 截断 5 条，字段长度截断。
- **评委**：
  - `score` 仅 1–5 或 null；`comment` ≤60 字；`question` ≤300 字；
  - `action` 非三态之一时回退 `next`；
  - 达到题数上限（普通 9 / 地狱 10）时服务端直接返回 `end`。
- **复盘**（`sanitize`）：
  - 维度分重建与 clamp；
  - `per_question` 仅保留真实题号；
  - `weaknesses` 仅保留 `source_round` 存在于实录的条目；
  - 历史漏洞判定按传入列表逐条回填，模型漏答默认 `untouched`；
  - 文本长度统一截断。

### 7.5 评分一致性与参数

| 路由 | maxTokens | temperature | 说明 |
| --- | --- | --- | --- |
| diagnose | 2500 | 1.0（默认） | 生成诊断报告 |
| judge | 800 | 0.5 | 降低随机性，保证同一回答评分稳定 |
| review | 4000 | 1.0（默认） | 汇总长文本生成复盘 |

### 7.6 演示模式（Mock 兜底）

触发条件：未配置 `DEEPSEEK_API_KEY`，或模型调用抛错（路由 catch 后返回 mock 并带 `degraded: true`）。

- **诊断 mock**：对 BP 文本做字符哈希，派生各维度比例与评语；返回固定优势与 5 条典型漏洞，标记 `mock: true`。
- **评委 mock**：按 `weaknesses` 与题库脚本化出题；答案评分用启发式（长度 + 是否含数字）；连续低分触发结束。
- **复盘 mock**：由现场评分均值折算维度分；失分题生成漏洞；历史漏洞按序号模拟复发/改善。

前端看到 `mock` 标记时展示「演示模式」横幅（`MockBanner`），不冒充真实 AI 输出。

### 7.7 人在回路（Human-in-the-loop）

- 所有 AI 评分/结论旁固定展示 `AIBadge`（「AI 生成，仅供参考」）。
- 漏洞必须用户点击「成立」才写入档案；「不成立」不入统计。
- AI 参考回答明确标注「请改写成自己的语言」。
- 页脚固定提示：最终判断结合指导教师意见。

## 9. API 设计

三条路由均为 `POST`、`runtime = "nodejs"`、无鉴权（本地/内网使用），服务端持有模型 Key。

### 9.1 `POST /api/diagnose`

| 项 | 内容 |
| --- | --- |
| 请求体 | `{ bp_text: string, competition: CompetitionId }` |
| 校验 | BP 去空格后 ≥50 字，否则 400 `{ error }` |
| 成功响应 | `DiagnosisReport`（`overall_score`、`dimensions[]`、`strengths[]`、`weaknesses[]`） |
| 兜底 | 无 Key → mock；调用失败 → mock + `degraded: true` |
| 输入截断 | BP 最多 8000 字 |

### 9.2 `POST /api/judge`

| 项 | 内容 |
| --- | --- |
| 请求体 | `competition, bp_summary, bp_text, diagnosis?, mode, persona, phase(start\|answer\|switch), asked[], user_answer?, pending_question?` |
| 结束条件 | `phase=answer` 且已完成题数 ≥ 上限（9/10）→ 直接返回 `end` |
| 成功响应 | `JudgeTurn`：`{ score: 1-5 \| null, comment, action: followup\|next\|end, question }` |
| 兜底 | 无 Key 或异常 → 脚本化 mock（异常时带 `mock: true`） |
| 输入截断 | BP 最多 6000 字 |

### 9.3 `POST /api/review`

| 项 | 内容 |
| --- | --- |
| 请求体 | `competition, bp_summary, diagnosis_overall?, prev_score?, records[], past_weaknesses?` |
| 校验 | `records` 非空，否则 400 |
| 成功响应 | `ReviewReport`（`overall_comment`、`dimension_scores[]`、`per_question[]`、`weaknesses[]`、`past_weakness_verdicts[]`、`next_suggestion`） |
| 兜底 | 无 Key → mock；异常 → mock + `degraded: true` |

**错误策略**：接口异常不向用户抛栈，统一降级为 mock 并在前端提示演示模式；网络错误由前端 catch 并通过表单/页面文案提示重试。

## 11. 隐私与安全

### 11.1 数据边界

- **训练数据（本地模式）**：团队、场次、问答、漏洞全部存于浏览器 `localStorage`，服务端无数据库、不落盘。
- **训练数据（云端模式，可选）**：登录后数据存 Supabase Postgres，行级安全隔离；数据边界与隐私口径随启用状态变化，详见 `docs/supabase-数据系统方案.md` 第十节。
- **BP 文本**：会随诊断/评委/复盘请求发送到服务端，再由服务端转发至 DeepSeek API 用于生成；应用本身不持久化。
- **API Key**：只存在于服务端环境变量 `.env.local`，浏览器不可见；`.gitignore` 排除 `.env*`。

### 11.2 风险与缓解

| 风险 | 现状 | 建议 |
| --- | --- | --- |
| Key 泄露 | 仅服务端读取 | 部署时注入环境变量；设置额度；定期轮换 |
| 公网滥用 | API 路由无鉴权/限流 | 公网部署前加登录、IP 限流或网关鉴权 |
| localStorage 清空 | 用户清理浏览器数据会丢失 | 提供导出/导入备份（见 `demo/备份-导出.js`、`demo/备份-导入.js`） |
| XSS | 全部文本经 React 转义，无 `dangerouslySetInnerHTML` | 保持此约束；导出 Markdown 在客户端生成 |
| 第三方数据政策 | BP 会传给模型服务商 | 在隐私说明中明确；需更强合规时替换私有化模型 |

## 12. 性能与稳定性

**已实现**

- 输入截断：诊断 8000 字、评委 6000 字、复盘按记录数自然限制。
- 结构化输出 + Sanitize，避免脏数据进入 UI。
- 模型异常自动降级 mock，前端横幅提示，不阻塞演示。
- React StrictMode 防重：诊断页 `startedRef`、复盘页 `reviewedRef`。
- 请求期间 `busy` 禁用输入与按钮，避免并发提交。
- 评分回写从 localStorage 现读，避免闭包陈旧值。

**已知限制**

- `localStorage` 写入无 `try/catch`，配额（约 5MB）耗尽时可能抛错。
- 模型请求无显式超时、无自动重试；网络抖动时依赖用户重试。
- 不做流式输出，长报告需等待完整 JSON。
- 无服务端缓存/队列；并发高时直接打模型 API。
- 无自动化测试与 CI，当前以 `tsc --noEmit` 与手工回归为主。

## 13. 部署与运维（`deploy.sh`）

1. 检查 Node.js（未安装时输出安装命令）。
2. 检查 `.env.local` 是否存在有效 `DEEPSEEK_API_KEY`；缺失仅警告，进入演示模式。
3. `npm install --no-audit --no-fund`。
4. `npm run build`。
5. 启动：优先 `pm2`（进程名 `luyan-peilian`，`PORT` 可配，默认 3000）；无 pm2 时 `nohup npm start`，日志写 `app.log`。

**推荐生产配置**：Nginx 反向代理 + HTTPS；`pm2 startup` 设置开机自启；限制 API 路由访问来源；定期更新依赖与 Key。
